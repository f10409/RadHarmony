RadHarmony evaluation pipeline

From the code you write to the report and the fix, end to end. Branch v0.2-dev, 2026-10-28. Built, tested and committed.

In one minute

The problem

The wiki had about 380 code blocks, and nothing ran them. The repo had no linter, no style check for prose and no guard for base-code edits.

A one-time audit on 2026-10-27 found 126 findings (about 118 different bugs), each with proof: 6 high, 63 medium, 57 low.

The goal

  • Find bugs with proof: a command and its output.
  • Keep the docs true to the code.
  • Turn each mistake into a check, so that it cannot come back.

3 parts

Before the 3 parts, an agent writes the code. For a new dataset, the add-dataset skill does this (tab Add a dataset).

1. Automatic checks

scripts/evalkit/run_all.py

When: each commit, CI, and inside /evaluate

Who: the computer, no agent

You get: pass or fail

2. /evaluate

a 3-part review with proof

When: each branch, or the whole repo before a release (--full)

Who: the main agent and up to 27 other agents

You get: a report, open questions and lessons

3. /fix <finding ids>

a failing test first, then the fix

When: after a maintainer picks the findings to fix

Who: the main agent

You get: fixed code or docs, each with a new test

What the agents compare the code with

2 main files. The tab "The flow" (last box) lists all of them.

eval/RULES.md

Rules with a check (L-001 to L-007, B-001, STE, ruff, BLOCK, CLAIM), and judgement rules J-01 to J-12 for the rules reviewer.

Example: J-06, "an evaluator does not use test labels to pick a threshold".

Implementation: add a dataset (/add-dataset)

The pipeline checks code, so an agent must write the code first. For a new dataset, the add-dataset skill does this. Its 13 steps are in .claude/skills/add-dataset/SKILL.md (900 lines). The add-backbone skill does the same job for a new image encoder.

The steps today

The step numbers in brackets are the numbers in SKILL.md.

1Describe the data (skill steps 1 to 4)
The agent writes the dataset config configs/datasets/<key>.json: paths, columns, labels and masks. It fills the missing fields from the CSV headers, the image folders and the DICOM headers. It asks the user only for what it cannot find.
2Confirm the image folder (skill step 4a)
The agent picks base_image_dir: the deepest folder that holds the entries of image_path directly. It checks that the 2 parts together give a real file or folder for one row. The user confirms the choice. Example (RSNA Pneumonia): base_image_dir is .../stage_2_train_images/, and image_path is <patientId>.dcm.
3Write the code (skill steps 5 to 9)

The agent reads a similar dataset first: CheXpert or MIMIC-CXR for 2-D, CT-RATE or RadChestCT for 3-D. Then it writes these parts:

  • the harmonizer in radharmony/harmonizer/<name>/, with _build_* steps such as _build_patient_id()
  • the dataset class in radharmony/dataset/<name>/, with @register_dataset("<key>")
  • the exports in the __init__.py files
  • a build function and a DATASET_REGISTRY entry in app.py
4Check (skill steps 10 and 11)
The agent goes through a checklist of 24 items, for example "LABEL_COLS sorted" and "SUPPORTED_OUTPUTS set". The agent runs scripts/check_datasets.py --datasets <key> --max-samples 30. It must exit with 0. The agent also adds the dataset to notebooks/datasets/dataset_integrity_check.ipynb.
5Write the docs (skill step 12)
The agent writes the wiki page docs/wiki/reference/datasets/<group>/<key>.md. Its fixed sections are Overview, Download, Expected layout, Label columns, Constructor arguments, samples, Harmonizer notes and Outputs. The agent adds a row to docs/wiki/reference/datasets/index.md and docs/wiki/index.md.
6Write what it learned (skill step 13)
The agent sums up what it learned. If a lesson is general, the agent edits SKILL.md by hand, for example with a new checklist item.

The skill does not change base code. If a change is necessary, the agent stops and asks the user first.

Gaps today

The skill is older than the pipeline. On 2026-10-28, these gaps were in it:

  1. No step adds the new key to configs/data_paths.json. The class gets a registry key from @register_dataset, so test_every_registry_key_has_an_entry fails in CI. The commit hook runs no pytest, so the commit passes. The bug hunters also find no data path for the new key.
  2. Skill step 11 says to add path constants near the top of scripts/check_datasets.py. That script now reads the paths from configs/data_paths.json. A /mnt/NAS path in a script also breaks rule L-006.
  3. The skill does not point to docs/wiki/design.md. It covers some decisions in its own words: sorted labels (D-05) and one class for each official split (D-09). It has no step for age in years (D-06) or one sex column (D-26).
  4. Skill step 13 puts a lesson into SKILL.md as text. Nothing turns it into a check. The pipeline turns a lesson into a check and a row in eval/RULES.md.
  5. The skill does not end with /evaluate.

Planned (skills upgrade, not started)

A second new step is decided (Frank Li, 2026-10-28): record the dataset stats before the code.

  • For each official split, the agent records the images, studies, patients, positives for each label, uncertain labels, and rows with boxes, masks or reports.
  • It also records the patients in 2 splits (must be 0), the sex counts and the age range.
  • The numbers come from 2 sources: the dataset paper or website, and the raw files read with pandas, with no RadHarmony code. Each difference gets a written reason, for example "the paper also counts the 500 patients of the hidden test set".
  • The stats go into an expected_stats block in configs/datasets/<key>.json. The config reviewer computes them again.
  • After the code exists, one shared test (tests/test_dataset_stats.py) compares harmonize() with expected_stats, exactly. It needs the NAS, so it runs in the full run, not in CI.
  • The wiki page states the same numbers with claim notes. So the docs and the test have one source.

Why: before 2026-10-28, only NODE21 had such a test (test_counts_match_the_paper). Example of a gap that it finds: the ChestX-ray14 wiki page says 25,596 test images, but harmonize() returned 24,716 (V-H1-2). The test now exists, with expected_stats for 5 datasets.

Part 1: automatic checks

scripts/evalkit/run_all.py runs 9 checks in 3 groups. There are 2 run types: a quick run (no NAS data, no GPU) and a full run. Pick where the run happens to see which checks run. The numbers are from the quick run on 2026-10-28.

GroupCheckWhat it findsExampleTodayIn this run

The known-problems lists

The lists are in eval/known_problems/<check>.json. An old problem passes for now. Only a new problem fails.

  • The key of a problem comes from the check, the rule, the file and the text. It does not use the line number. So a problem that moves to another line is still old.
  • After a fix, run_all.py --update-known --full writes the lists again. It needs the NAS.
  • A list must not grow. run_all.py --check-shrink origin/main fails if a list grew since that commit. CI runs this check on each PR. Exception: a new rule that you name with --new-rule can add its old problems to a list (D-45).
  • The shrink check works only for lists that are already on main. Today no list is on main.

Doc code block notes

A note on the line before a code block tells the runner what to do. A skip needs a reason.

<!-- block: run=ci|local|gpu|skip data=<key> timeout=300 reason="..." -->

Example: <!-- block: run=local data=chexpert_train --> runs the block only in a full run, with the CheXpert data from the NAS. The runner compiles a block with no note, and runs it only in a full run.

A whole-repo review has these 27 agents, plus the main agent. At most 10 agents run at the same time. The briefs are in .claude/skills/evaluate/references/.

Why 2 bug hunters and a checker? Two different models miss different bugs. The checker did not write the findings, so it has no reason to keep a weak one. It runs each command again and keeps a finding only if the output shows the failure. Review agents start fresh: they get their brief, not the main agent's guesses.

A finding needs proof

Correct?

a command, its output, and the expected output (from the intent file or a design decision)

Follows our rules?

the rule ID and a quote of the code or text

Does what was asked?

a quote of the request, and what the code does

Example from the first whole-repo review (shortened):

{
  "id": "V-H1-23",
  "found_by": ["opus"],
  "title": "ChestX-ray14 train/test split is lost in harmonized_df",
  "command": ".venv/bin/python reports/eval/2026-10-27-full/correct/H1_opus/repro_cxr14_split_state.py",
  "output": "ChestXray14TestHarmonizer: harmonize() returned 24716 rows | h.harmonized_df 111240 rows",
  "expected": "harmonized_df has the same 24,716 test rows as the harmonize() return value",
  "severity": "medium",
  "severity_changed": "high -> medium on 2026-10-28: no current benchmark uses this path"
}

Severity

  • high: it changes a benchmark number or a training or evaluation result.
  • medium: wrong output, but no current benchmark number changes. Or a crash on a call that the docs show.
  • low: code that nothing calls, a wrong docstring or message, or an edge case.

A finding whose cause is in base code gets touches_base_code: true. /fix asks before it changes base code for such a finding.

Open questions

Sometimes no design decision covers a behavior, and the agent cannot tell if it is a bug. Then the agent writes an open question, not a finding. The checker merges the questions of the 2 bug hunters. merge.py merges questions with the same text and gives each one an ID (Q-1, Q-2). The main agent asks you about each one.

"open_questions": [{"question": "...", "today": "what the code does",
                    "evidence": "command and output", "options": ["...", "..."]}]

The report

  1. The run facts: date, branch, commit, scope and agents.
  2. Automatic checks.
  3. Correct?
  4. Follows our rules?
  5. Does what was asked?
  6. Compared with the last whole-repo review (--full only): still open, fixed or cannot run.
  7. Coverage and BLOCKED: what the agents could not test, and why.
  8. Open questions.
  9. Lessons, in 7 groups. Examples: "automatic checks to add" (a draft rule for eval/RULES.md) and "tool cost" (an agent that stopped before it wrote its file). The other groups: where the findings were, judgement rules, CLAUDE.md size, rules that change nothing, and missing information.

The 3 review parts stay separate. The report does not merge or rank them across parts.

Decisions, one item at a time

The checklist is .claude/skills/evaluate/references/decisions.md. /evaluate uses it in step 6. /fix uses it before a base-code edit or a new rule.

When

  • an open question
  • a base-code change
  • a draft rule
  • a fix with more than one correct behavior
  • a severity change

Order in /evaluate: open questions, then severity changes, then draft rules. Inside each group: high, then medium, then low. /fix asks about a base-code change or a fix with more than one correct behavior when it comes to one.

For each item

  1. Check the facts first.
  2. Say what the code does today, with an example.
  3. Give a recommendation, the reason and the cost.
  4. Ask one question with 2 or 3 options. The recommendation is first. An open question also gets "Leave open".
  5. Read the whole answer and any note that comes with it.
  6. Record the answer before the next item.

Where the answer goes

AnswerWhere it goes
a design decisiona D- entry in docs/wiki/design.md, with the name and the date
leave opena D- entry with the status "Open" in docs/wiki/design.md. It keeps its ID when a maintainer decides it.

a base-code changethe 5 steps in CLAUDE.md: ask first, warn after the edit, BASE CODE CHANGE: in the commit, the PR section, a final warning

Example: on 2026-10-28, open question O-1 in docs/wiki/design.md asked what h.harmonized_df must hold after h.harmonize(). Then the ChestX-ray14 test harmonizer returned 24,716 rows, but h.harmonized_df held 111,240. Frank Li chose "the same rows as harmonize()". It is now decision D-24. V-H1-23 was its known gap (fixed on 2026-10-28).

The 33 design decisions

A known gap is a place where the code breaks a decision today. It is a bug to fix. Each gap is one line with its finding ID. reports/eval/index.json gives the run folder of each ID. An agent reports a known gap again only in a new place. /fix removes a gap when it fixes it.

  • Decided: a maintainer chose it. The entry names the person and the date, or the file that records it.
  • Decided, planned: chosen, but not built yet. A missing feature here is not a bug.
  • From the code: the code does it today, and no maintainer has confirmed it yet.
  • Open: not decided yet. The entry gives the question, what the code does today and the options. It keeps its ID when a maintainer decides it. No entry is open today.

New rules (lessons)

  1. A mistake happens 2 times, or one time with a large effect. Make it a rule.
  2. If a computer can check the rule, write the check first: a test in tests/test_lessons.py or a check in scripts/evalkit/lessons.py.
  3. Prove the check with prove_rule.py. It must fail on the commit with the mistake and pass on the fix.
  4. Add a row to eval/RULES.md. If a computer cannot check the rule, add a judgement rule.
python scripts/evalkit/prove_rule.py --bad 95bb587^ --good 95bb587 \
    --with tests/test_lessons.py --with scripts/dataset_paths.py --with configs/data_paths.json \
    -- tests/test_lessons.py::test_l001_chexpert_age_years_is_filled

This proves rule L-001 (a declared age source fills age_years). The test fails on the commit before the CheXpert age fix and passes on the fix.
