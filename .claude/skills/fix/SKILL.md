# /fix <finding ids>

Fix only the findings that the user names. If the user names no finding but has a report, ask which findings to fix.
If the user asks for a new doc change with no report, ask if a branch review (`/evaluate`) is wanted first. Else make the change, then do "Proof at the end".

Find the run folder of each ID in `reports/eval/index.json`. Read the finding from `findings.json` in that folder. A check finding (C-) is in its `check_findings` list.
The rules are in `eval/RULES.md`. Before a code or doc change, read `CLAUDE.md`, section "Design decisions and rules". It sends you to `docs/wiki/design.md`.

**No user to ask.** A sub-agent or a headless run has no user. Then write the question and the chosen answer in the report, and go on.

## For each finding

1. **Read the finding.** Run its command again. If the failure does not show, tell the user and skip the finding.
   - A check finding (C-) has the command `run_all.py --group <group>`. Use its `narrow_command` when it has one, because it checks only the file of the finding. The new line of the output must name the file, the line and the rule of the finding. Another finding can fail the same check.
   - A Follows our rules? finding (R-) or a Does what was asked? finding (A-) has no command. Open its file and line, and confirm the quote.
2. **A choice for the user?** Stop and ask in these 2 cases. Ask one item at a time, with `.claude/skills/evaluate/references/decisions.md`.
   - **Base code.** The fix needs a base file (`CLAUDE.md` list, or any `class Base...`). Follow `CLAUDE.md`, section "Base code needs explicit approval".
   - **More than one correct behavior.** `docs/wiki/design.md` does not choose between them. Ask before you write the test.

   A doc finding is not such a choice: the code is the spec. If `docs/wiki/design.md` or the source data says that the code is wrong, it is a code finding (rule J-09). Fix the code, not the doc.
3. **Write the failing test first.**
   - Code finding: turn the proof script into a test in the matching `tests/test_<area>.py`. The expected value comes from the source data or the spec, not from the code (rule J-08). If the test needs real data, read the path at import time with `paths("<key>", missing_ok=True).get("<arg>", "")`. Then skip with `pytest.mark.skipif(not os.path.isfile(...))` (or `isdir`), as `tests/test_node21.py` does. A plain `paths("<key>")` raises `MissingPathsError` at collection when the key has no entry.
   - Count finding of a dataset (rows, patients, labels): add the expected value to `expected_stats` in `configs/datasets/<name>.json`, under the registry key of the split. Run `.venv/bin/python -m pytest tests/test_dataset_stats.py -k <key>`. It needs the data folders from the data paths file (`docs/wiki/get-started/install.md`, "Data paths for the checks"). If `paths()` raises `MissingPathsError`, ask the user: add the entry, give the folder for this run, or skip the check and say so.
   - Check finding (C-), or a doc finding with an automatic check: the run of step 1 is the failing check. Do not run it again.
   - R- finding about code (for example rule J-04): write a test, as for a code finding.
   - R- finding about prose (for example rule J-10 or J-11): no test can find it. The "failing test" is the quote and the rule. Show both to the user before the fix.
   - A- finding: write a test of the quoted request. If the request cannot be a test, treat it as a prose R- finding. Show the quote of the request and what is missing.
   - Run the new test (not for a prose finding). It must fail for the reason in the finding.
4. **Fix.** Make the smallest change that makes the test pass. Do not hide a code bug with a doc edit (rule J-09). Keep the code style of the file.
   - The text with a style problem can also state a wrong fact. Then fix the fact too, and tell the user.
   - A generated page has the line "Generated by ... Do not edit". Edit its source, then run its script. Example, dev repo only (`configs/data_paths.json` is in git): edit the file, then run `.venv/bin/python scripts/gen_nas_paths_page.py`. A new entry there needs `verified`. Do not run the script on a user's own paths file.
5. **Check.**
   - Run the new test, and the command of the finding (or its `narrow_command`). Both must now show the right result.
   - Prose finding: read the file again. The quote is gone, or it is changed as the rule asks.
   - Run `git diff` on each changed file. It must show only the planned change. For example, a deleted blank line before a `<!-- block: -->` note is a side effect.
   - Run `.venv/bin/python scripts/evalkit/run_all.py --group lint,docs` (fast). It can still show the other findings of this `/fix` run. After the last finding, it must pass. The full run is in "Proof at the end".
   - A known problem is gone when the `fixed` column of the table is above 0. Then run `run_all.py --update-known`, then `run_all.py --check-shrink HEAD`. The lists may only get shorter. Add `--full` to `--update-known` only in the dev repo with the NAS mounted: `.venv/bin/python -m pytest tests/test_data_paths.py -k paths_exist_on_nas -q` reports passed tests, not skipped ones. Without `--full`, the `claims` and `blocks_run` lists stay as they are. `--update-known` runs pytest too, so run it in the background (see "Proof at the end").
   - If the fix closes a known gap in `docs/wiki/design.md`, remove that gap line. If `eval/TODO.md` has an item for the gap, tick it.
6. **Show the user** the diff (the real code) and why. Run the critic review from the user's `CLAUDE.md` if the change is large.

## Lessons
A computer can check some judgement findings. For example, a test can compare the label names with the `cls` order (J-04). For such a finding, propose a new rule with a check.

To propose a new rule, follow `eval/RULES.md`, section "How to add a rule (lessons)". Ask the user about each new rule with `.claude/skills/evaluate/references/decisions.md`.
Build each rule that the user approved, here or in an `/evaluate` report. Add the check, prove it, then add the row.

## Proof at the end
1. Run `.venv/bin/python scripts/evalkit/run_all.py` once. It must pass. Add `--full` only in the dev repo with the NAS mounted (the test in step 5).
   - The full run takes more than 1 hour on the lab server, because it runs all of pytest. Run it in the background (`run_in_background`), and wait for the notice. Do not run it in the foreground.
   - It prints one line when each check ends, so you can see which check runs.
2. Run `/evaluate` on your fixes (branch review).
   - All fixes are doc fixes that an automatic check covers: ask the user if a branch review is wanted. The passing check is the proof.
   - Fixes not committed: use `--base <current branch>`. Then the scope is the uncommitted changes (`git status`). Tell the user if the scope also has changes that are not yours.
   - Fixes committed: use `--base <the commit before the first fix>`.
   - If `/evaluate` reports an open high finding, fix it with steps 1 to 6, or tell the user why not.

## Done when
- Each named finding is fixed. It has a new test, or the existing check that reports it, or the quote check of a prose finding. Or the user knows why it was skipped.
- `run_all.py` passes and the known-problems lists did not grow.
- `/evaluate` on your fixes reports no open high finding, or the user said that the passing check is enough.
- Base-code changes have the user's approval and the `CLAUDE.md` warnings.
- Nothing is committed unless the user asked for a commit.
